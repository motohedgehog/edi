# Investigate failures and performance

Use this procedure to explain a failure before changing its cause. Diagnostics must follow the root privacy rules, including temporary instrumentation and captured fixtures.

1. Establish the symptom: expected behavior, observed behavior, inputs, environment, and the smallest known reproduction. Preserve the failing test name, relevant revision, or shuffle seed. Separate observations from assumptions. If reproduction is unavailable, state what evidence is missing and investigate the reachable paths without claiming a confirmed cause.
2. Reduce the case. Run the affected test or operation in isolation, then compare with the failing environment. Trace data and state backward from the failure through callers and validation. Inspect recent relevant changes when useful. For flaky tests, check shared state, real-time waits, cleanup, and ordering before increasing timeouts or retries.
3. Choose one hypothesis and the smallest observation that could disprove it. Use targeted assertions for state, the race detector for shared-memory problems, and goroutine/block profiles for hangs. Escalate to tracing or a debugger only when simpler evidence is insufficient. Keep temporary diagnostics local and sanitized; do not add a production diagnostic endpoint by default.
4. For performance, define the metric and representative workload first. Distinguish upstream or database latency from work inside the process. Capture a baseline and profile the relevant CPU, allocation, or contention cost. Measure candidate changes serially with repeated benchmark runs on the same toolchain, hardware, and inputs. Keep setup outside the measured operation and use allocation measurements when relevant. Use statistical comparison when available; do not claim a speedup from a noisy single run.
5. Fix the demonstrated cause in the shared implementation. Add a regression test that fails for the original behavior, then verify the fix and affected callers. Change one variable at a time. If successive fixes fail, revisit the model instead of accumulating workarounds. Remove temporary instrumentation once it has served its purpose.

Finish with the cause, evidence, regression result, and applicable root checks. For optimizations, report the workload and comparable before/after measurements. Identify any part of the original symptom that remains unverified.
