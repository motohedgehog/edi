# Change repository tooling

Use this procedure for dependencies, lint/build configuration, containers, CI, and release automation. Read the affected configuration before editing it; it is authoritative for versions, flags, platforms, and enabled checks.

1. Identify the affected path from source to artifact. Inspect `go.mod`, `go.sum`, `Makefile`, `.golangci.yml`, `Dockerfile`, or `.github/workflows` as applicable. For release changes, also inspect the cliff configuration. Reuse these mechanisms and keep changes limited to the requested behavior.
2. For dependencies, first check existing packages and the standard library. Justify additions by capability, maintenance, license, and compatibility. Consult documentation for the selected version rather than copying a catalog recommendation. Keep updates targeted; review compatibility notes for persistence, serialization, networking, and public contracts. Update `go.mod` and `go.sum` together, inspect `go mod tidy` changes, and run tests and the existing vulnerability check when dependencies change. Keep toolchain changes aligned with the container builder and CI configuration.
3. For linting, keep `.golangci.yml` as the rule source. Fix the cause before suppressing a diagnostic; a suppression must name the linter and explain the local exception. Do not disable a rule globally to hide one finding. Use `make fmt-check` to inspect formatting and `make fmt` when formatting changes are intended. Check the resulting diff for unrelated edits.
4. For containers, retain separate build and minimal runtime stages, a non-root runtime user, certificate availability, timezone support, and writable data-directory requirements. Keep credentials out of build arguments and image layers. Preserve dependency-layer caching, pinned base images, and `.dockerignore` protections. Build locally with `make container`: its default is `container` on macOS and `docker` elsewhere; override with `CONTAINER_ENGINE`. On macOS, check `container system status` and start the service with `container system start` if needed. Use the local service, not a remote Docker context.
5. For CI and releases, preserve pinned actions and narrowly scoped permissions. Keep untrusted pull-request work separate from publishing credentials. Preserve tests, vulnerability scans, and artifact verification before publication; publish the artifacts that passed those checks. Keep release notes tied to the actual commit range using the existing cliff configuration. Describe user-visible changes and upgrade actions without unsupported claims.

Finish with the root checks plus checks for the changed surface: dependency tests and vulnerability results, lint configuration validation, container build and `-version` smoke test, or workflow trigger/permission/artifact-path inspection. Report which execution paths were verified locally and which still require CI. Verification does not require publishing a release.
